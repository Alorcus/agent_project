Write path

A fact is one sentence, so there is no chunking

Extraction runs after a reply, over a sliding window of six countable turns stepping four — the two carried turns are what let a claim span the boundary. The window arithmetic is derived from the stored watermark on every call, never held in memory between them.

Read path

Gate, then rewrite → retrieve → assemble → judge

Most turns never reach the corpus: the gate answers in one word, and KNOWN ends it. What follows is a bounded loop whose only escape hatches are the judge, the round cap, and the clock. Assembly is the one stage with no model call in it.

The gate is deliberately biased. An unparseable verdict is not a third outcome — it means retrieve. A needless search costs a few seconds; a skipped one produces a fluent, confident, wrong answer.
Fan-out

Why the cap is 15 queries, not 9

Three rounds of three rewrites would be nine. It is fifteen because the loop widens after the first verdict: round one has exactly one seed — the user's own message — while a reseed may name up to two leads, and each lead gets its own full expansion.

The worst-case call budget follows from the same arithmetic: 1 gate + (3 + judge + reseed) + (6 + judge + reseed) + (6 + judge) = 21 calls before a token of the reply is generated. Cost grows with the product of the knobs, not their sum — which is why recall_seeds is clamped at construction and again in parse_seeds, rather than merely requested in the prompt.

What the model actually receives

<the user's message, verbatim>

---
The notes below were retrieved from the user's earlier
conversations in this project. The user did not write them
and cannot see them. [+ hedge, on a cap exit]

Facts:
- The team chose Postgres 14 for the billing service.

Said:
- Ada: "we're going with 14, the extension we need landed there"

The user's message, again: <the user's message>

The message is restated after the digest because a long block of retrieved material otherwise buries the question it was retrieved for. Both the injected block and the transcript note render through recall_block, so what the model saw and what the note shows cannot drift.

No recall runs alongside a specialist consultation — and the gate call is not spent either, because recall is never entered on that path.
Where it lives
core/prompts.py — gate, rewrite, judge, reseed and injection text; every prompt, and nothing else
core/retrieval.py — the loop, and the only module that reads fact_embeddings
core/facts.py — the sliding window, derived from the watermark on every call

llm/embedding.py — the encoder, loaded by path, never downloaded
